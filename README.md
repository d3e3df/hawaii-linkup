# LinkUp

## Лабораторная работа №1

В рамках Лабораторной работы №1 были спроектированы четыре самостоятельных сервисных контракта (A, B, C, D), решающих изолированные задачи предметной области.

### Описание Реализованных Контрактов

* **Контракт A (`discovery.Service`)**: Реализует многокритериальный поиск потенциальных кандидатов по структурированному набору параметров `Criteria`, включая город, возрастной интервал (`MinAge`, `MaxAge`) и совпадение по списку интересов. Сервис работает исключительно с подготовленным набором данных и возвращает список кандидатов.

* **Контракт B (`feed.Service`)**: Отвечает за динамическое формирование персональной выдачи (ленты) кандидатов для запрашивающего пользователя. Сервис автоматически отсекает кандидатов, не удовлетворяющих условиям показа: заблокированных пользователей, неактивные аккаунты, самого запрашивающего пользователя, а также профили, которым пользователь уже выразил симпатию.

* **Контракт C (`eligibility.Service`)**: Выполняет бизнес-проверку допустимости совершения действия (лайка) актером в отношении целевого пользователя. Сервис возвращает вердикт `Decision{Allowed: bool, Reason: Reason}` (где `Reason` — типизированная строка). В случае невозможности взаимодействия вердикт содержит явную причину отказа: `already_liked` (уже лайкнут), `blocked` (пользователь заблокирован), `inactive` (профиль неактивен), `self_like` (попытка выразить симпатию самому себе).

* **Контракт D (`interaction.Service`)**: Выполняет команду лайка (Application-команда). Сервис загружает данные сторон, проверяет наличие встречного лайка и использует чистую функцию `Decide` для вычисления исхода (`OutcomePending`, `OutcomeMatch` или `OutcomeRejected`). Если исход не `OutcomeRejected`, сервис сохраняет лайк в хранилище через `SaveLike`. Если исход `OutcomeRejected` (например, самолайк или неактивный профиль), запись в хранилище не производится, а сервис возвращает соответствующий статус.

## Лабораторная работа №2

*  **Доменная модель (`domain.Pair` и `domain.PairKey`)**: Представляет собой единый источник истины о взаимодействии двух пользователей. `PairKey` гарантирует, что пара `(u1, u2)` и `(u2, u1)` идентифицируется одинаково (с автоматической сортировкой ID). Сама структура `Pair` хранит только флаги лайков (`LowLiked`, `HighLiked`), а производные признаки (`IsMatch`, `LikeCount`) вычисляются динамически, что исключает их рассинхронизацию. Метод `WithLike` реализует иммутабельный переход: возвращает новую копию пары, не изменяя исходную.

*  **Контракт (команда) `reaction.Service`**: Выступает в роли Application-команды (сквозного сценария), которая связывает чтение, проверку правил и запись. Сервис загружает данные пользователей и текущее состояние пары из хранилища, проверяет наличие блокировки, а затем использует чистую функцию `Transition`. Если переход допустим и состояние изменилось, сервис сохраняет новую пару в хранилище через `SavePair`. При повторе действия (когда лайк уже стоит) или при бизнес-отказе (например, блокировка) запись не производится, а сервис возвращает корректный результат (`Result`) с флагом `Changed=false` или ошибку.

*  **Чистое правило (`reaction.Transition`)**: Инкапсулирует бизнес-логику перехода состояния. Функция не выполняет I/O и не мутирует входные данные. Она проверяет соответствие пары лайкающим пользователям, вызывает ранее созданные правила допустимости (`eligibility.Check`) и вычисления исхода (`interaction.Decide`), после чего возвращает `Decision` с новым состоянием пары и флагом изменения. Это позволяет тестировать бизнес-логику изолированно от хранилища.

*  **Интеграционный сценарий (`scenario_test.go`)**: Проверяет сквозной пользовательский путь на реальном in-memory хранилище (с декоратором для подсчета вызовов `Save` и эмуляции отказа записи). Демонстрирует, что после первого лайка состояние меняется, при повторе — нет, а взаимный лайк создает матч, который корректно отражается в смежных сервисах (лента `feed` исключает сматченных, а `eligibility` возвращает `already_liked`).

## Лабораторная работа №3

В рамках Лабораторной работы №3 прежние сервисные контракты объединены в запускаемое HTTP-приложение. Добавлены отдельная локальная зависимость Profile API, пагинация выдачи, атомарное обновление общего состояния, конфигурация через environment, журналирование и корректное завершение активных запросов. Пользовательский путь сохранён: получить кандидатов → поставить Like → повторить команду без новой записи → прочитать состояние пары → выполнить встречный Like и получить match.

### Описание реализованных компонентов

* **HTTP-слой (`internal/httpapi`)**: Реализует маршруты `GET /v1/me/discovery`, `PUT /v1/me/likes/{targetID}`, `GET /v1/me/pairs/{targetID}` и `GET /healthz`. Handlers используют явные DTO и преобразуют предметные ошибки в HTTP-статусы и JSON-коды. До вызова Application-логики проверяются path, query, тело запроса и заголовок `X-Demo-User`. Каждый ответ получает серверный `X-Request-ID`, а в `slog` записываются метод, route pattern, статус и длительность без полного тела запроса.

* **Выдача с фильтрацией и пагинацией (`feed.Service.Page`)**: Расширяет прежние правила ленты параметрами `interest`, `limit` и `offset`. Фильтр по интересу очищается от пробелов и приводится к нижнему регистру. Сначала исключаются недопустимые кандидаты и применяется предметный фильтр, затем выполняется пагинация. `limit` по умолчанию равен 20 и находится в диапазоне 1..50, `offset` по умолчанию равен 0. Пустая страница возвращается как `"items":[]` с сохранением стабильного порядка fixtures.

* **Команда Like и атомарное состояние (`reaction.Service`, `memory.Store`)**: Объединяет прежние `eligibility.Check`, `interaction.Decide` и `reaction.Transition` с обращением к Profile API. Первый допустимый Like возвращает `changed:true`, повтор в неизменных условиях — `changed:false` без новой записи, а создавший match запрос — `matched_now:true`. Метод `UpdatePair` под `sync.RWMutex` объединяет чтение пары, проверку блокировки, чистый переход и сохранение. Сетевой вызов выполняется до захвата mutex. Чтение отсутствующей пары возвращает начальное состояние, а не ошибку.

* **Локальная HTTP-зависимость (`internal/profileapi`, `cmd/profileapi`)**: Запускается отдельным процессом и поддерживает режимы `ok`, `missing`, `error`, `slow` и `large`. Режим переключается через служебный `PUT /_admin/mode/{mode}` без изменения исходного кода. Это позволяет воспроизводить отсутствие профиля, ошибку, задержку и превышение размера ответа без обращения к публичному API.

* **HTTP-клиент Profile API (`internal/adapter/profilehttp`)**: Использует общий переиспользуемый `http.Client`, настраиваемый base URL и `NewRequestWithContext`. Предусмотрены отдельные timeout, закрытие тела ответа, ограничение чтения `L+1`, строгая проверка JSON и совпадения возвращённого ID с запрошенным. Контекст команды передаётся из HTTP-handler в клиент без создания независимого внутреннего бюджета.

* **Сборка и завершение (`internal/config`, `internal/app`, `cmd/linkup`)**: Создают хранилище, use cases, HTTP-клиент, handlers, `ServeMux` и явный `http.Server`. Настройки считываются из environment и проверяются при запуске. При SIGINT/SIGTERM приложение вызывает `Shutdown` с независимым grace context: активные запросы дожидаются завершения, а после deadline выполняются принудительное `Close` и сообщение об ошибке.

Полный контракт маршрутов, DTO, ошибок и ограничений находится в [api-contract.md](api-contract.md).

#### Воспроизводимый `.http`-сценарий

Полный сценарий находится в [lr3.http](lr3.http). Он включает фильтрацию и две страницы, исходное состояние пары, Like/no-op/match, чтение выдачи, пустые страницы, неверный ввод и предметный запрет, четыре отказа зависимости с возвратом в `ok`, конкурентные запросы и shutdown с активным запросом. Над каждым запросом указаны ожидаемый HTTP-статус и существенные JSON-поля.

Для реальной одновременной отправки запросов 5.1 и 5.2 после раздела 4 выполнить в терминале:

```bash
curl -sS -w '\nHTTP %{http_code}\n' -X PUT -H 'X-Demo-User: u2' \
  http://127.0.0.1:8080/v1/me/likes/u4 > /tmp/linkup-u2-u4.txt &
first=$!
curl -sS -w '\nHTTP %{http_code}\n' -X PUT -H 'X-Demo-User: u4' \
  http://127.0.0.1:8080/v1/me/likes/u2 > /tmp/linkup-u4-u2.txt &
second=$!
wait "$first" "$second"
cat /tmp/linkup-u2-u4.txt /tmp/linkup-u4-u2.txt
rm /tmp/linkup-u2-u4.txt /tmp/linkup-u4-u2.txt
```

Ожидание: оба ответа имеют статус 200 и `changed:true`; `matched_now:true` встречается ровно один раз. Порядок ответов не фиксирован. Затем выполнить запросы 5.3 и 5.4 из `.http`-файла.
